# 0.2 feature inventory and port gaps

Snapshot of `develop` on 2026-10-12. Core 0.2 = `packages/mantle` (`0.2.0-alpha.6`) plus `packages/mantle-ui` (Admin SPA, MCP App, kit). Port target = `packages/mantle-next` (`0.2.0-next.0`, ~1.9k lines under `src/`), `docs/next/*`, and open draft PRs #1489 (web.ts), #1490 (REST), #1491 (MCP) which are NOT merged.

Conventions
- Paths are relative to `packages/mantle/src/` ("core:") or `packages/mantle-ui/` ("ui:") unless absolute. Line numbers were taken from `Read`/`grep -n` on the current tree and are absolute.
- Row IDs are stable. Table A (what 0.2 does) and Table B (what Next has) share them. Section 4 groups the gaps into work packages that cite the IDs.
- Status vocabulary in Table B: `merged` (on develop), `PR#nnnn` (draft, not merged), `gap`, `partial`, `dropped` (removed by a recorded decision), `conflict` (decisions disagree, see section 1), `delta` (exists but wire/behaviour differs).
- Area = the section heading of the table plus the ID prefix: ADM (Admin API), EXT (Admin extensions), UI (Admin SPA), DEV (developer console), MCP, AUTH, SM (site/brand/media/email port), SRCH, TR (translations/locales), K (kernel behaviours, service composition, CLI).
- No 0.2 feature depends on a Queue: after-hooks run after commit in the request and `docs/handbook/reference/features.md` lists queue-deferred hooks under "Not in 0.2.0". Other dependency kinds that do appear: Better Auth plugins, R2, an email provider, KV (session cache), D1/PostgreSQL FTS, ASSETS binding, Cloudflare cron.
- 22 Admin languages are one feature (UI-27); per-key strings are not listed.

## 0. Headline findings

1. Next on develop is a generation kernel only: typed SQL Views/Procedures, a generic Store (find/first/count/insert/update/delete, keyset cursors, OCC, scope/TTL/publishing row rules), opt-in `publishing` transitions, typed ref `Handlers`, Better Auth DB adapter + schema, `resolveCaller` (session cookie and OAuth bearer), generated validation/paging/wire errors, Wrangler build. It has NO Admin, no MCP, no REST, no site/media, no email, no staff directory, no consent pages, no search, no translations, no TTL sweep. (`docs/next/compatibility.md`, `packages/mantle-next/src/**`.)
2. Draft PRs add: REST (#1490: `GET /api/views/<name>`, HTTP Triggers, origin check, 405+Allow, 1,000,000-byte body cap), MCP (#1491: `/mcp`, `/mcp/staff`, `query_view_<name>` tools, MCP Trigger tools, staff publishing tools, scope floor + challenges, lazy SDK), web (#1489: `/llms.txt`, `/sitemap.xml`, `.md` alternates, head tags; this is new in Next, 0.2 Core never shipped it: `docs/handbook/reference/features.md` "Not in 0.2.0").
3. Issue #1465 (decision dated 2026-10-12, "No visible regression") says every 0.2 Admin UI feature is ported and translations ship in 0.2.0. `docs/next/compatibility.md`, `usecase/refusals.ts` and issue #1477 still say the opposite. See section 1.
4. Security-relevant gap: Next `resolveCaller` (`packages/mantle-next/src/auth/caller.ts:55`) verifies the OAuth bearer and re-reads user role/ban, but does NOT bind the token to a live consent and session as 0.2 does (`core:auth/oauthTokens.ts:61` `assertActiveUserGrant`, claim `mantle_consent_id` added at `core:auth/buildAuth.ts:133-139` and `:272-291`). Without it, "Disconnect" on the connected-apps page (AUTH-11) would not stop already-issued tokens. Treat as a blocker for the OAuth/MCP package, not a nice-to-have.
5. Hidden wire constraints that make "reuse the SPA" non-trivial are in section 5.

## 1. Decisions (resolved 2026-10-12, #1465)

| # | Topic | Decision |
|---|---|---|
| C1 | Admin scope | Full port: every 0.2 Admin feature (no visible regression). #1477 is rewritten accordingly. |
| C2 | Translations | In 0.2.0: remove the `localized`/`translates` refusals (WP-K2); #1489 gains per-locale output after WP-K2. |
| C3 | Media/site/email | OSS ships them as optional generated modules in the package (WP-S1, WP-I3); Mantle Cloud wires R2, email OTP and email sending by default. |
| C4 | Staff roles | #1492: OSS has one role, `staff`, and every 0.2 role gate becomes "is staff"; the staff screens list staff and members, grant/revoke `staff` and invite. Role sets (owner/editor/contributor and custom), member tiers and organizations are Cloud, injected through an Admin extension and the deploy-time auth config. `Caller.role` becomes an open string. |
| C5 | Search | Build it in the kernel (WP-K1). |
| C6 | Lifecycle default | `operational` stays the default (no existing apps); Admin chrome follows each Schema's declared lifecycle. |
| C7 | MCP tool names | Match 0.2: snake-cased View/Procedure names, no `query_view_` prefix (#1491); WebMCP follows. |

WP-D0 is therefore reduced to doc reconciliation inside the packages that touch those docs.

## 5. Wire and behaviour constraints the Admin/MCP port must handle (hidden costs of "reuse the SPA")

1. Field spelling. 0.2 Admin entries and View rows use declared property names (`s.names` map, `core:admin/createAdminSurface.ts:79`, `:182`); Next Store rows and View outputs use lower-case storage names (`requestnumber`, `created_at`; README and contract.md). The SPA indexes `schema.properties[name]` and `collection.list.columns` by declared name. Needs a mapping layer in `admin.ts` (generated name tables).
2. Timestamps. 0.2 list items carry `updated_at` as epoch milliseconds (`ms()` at `:100`) and the SPA formats with `formatTimestampMs`; Next returns ISO strings with six fractional digits (contract.md "Date-time wire form"). Also `created_at`/`updated_at` native columns in staff View outputs (`NATIVE_OUTPUT_TYPES`) and `date`/`date-time` fields in `data` (ISO).
3. Lifecycle default and chrome. Collections with no `lifecycle` become `operational` (C6): no status column, no publish bar; Admin's nav groups (Content vs Records) change for unmarked Schemas. Next adds `published_at` and an `archived` state with a transition procedure the 0.2 Admin never exposed (optional UI action).
4. Index prerequisites. Store `orderBy` and generated View paging need indexed NOT NULL columns; the Admin default sort (`updatedAt`, tie-break `id`) needs the `(updated_at, id)` index that Next intentionally omits unless an Admin surface is selected (contract.md "Initial DDL decision"). 0.2's `sortableFields` rule (first field of a declared index and `required`) is already the same restriction.
5. Error and result shapes. 0.2: `{error: diagnostic}` with `code,message,path,expected,candidates,failure{outcome,retry}` (`redactForWire`); Next `wire()`: `{error:{code,message,path}}` only. The controller decides "uncertain" from codes `OUTCOME_UNKNOWN, PARTIAL_FAILURE, OUTPUT_VALIDATION_FAILED, INTERNAL_ERROR` (`ui:src/controller/index.ts` `UNCERTAIN_CODES`), so `OUTCOME_UNKNOWN` (503) still works; `PARTIAL_FAILURE` exists for media delete (SM-04). Procedure results: 0.2 returns the validated `output`; Next returns raw `{results: rows[][]}` ("not a claim of validated authored output"), so `POST /admin/api/operations/{name}` `{ok, output}`, REST bodies and MCP `structuredContent` need a decided mapping.
6. Cursors and paging. Cursor strings differ (Next keyset JSON codec; selected View cursors carry operation provenance). Admin is forward-only with cursor stacks in the URL, so only opacity matters; `cursor_direction=backward` stays refused on entries (members still use it, AUTH-14).
7. Validation. 0.2 validated every Admin write against the Schema (draft = partial, publish and operational = full) inside Store. Next Store is "a compile-time contract": `admin.ts` must run generated validators on untrusted JSON (null handling, `additionalProperties`, enum, format) and must not let `data` set native columns (`id,status,version,createdAt,updatedAt,authorId`).
8. Authorization semantics. 0.2 Admin entry routes ignore atom `requires` and rely on Store row rules plus per-route roles (handbook "Roles"); Next Store likewise "does not enforce a View's or Procedure's `requires`" and has "no role-based edit/delete rule", so Admin must carry the 0.2 role gates (contributor drafts only, editor publish/delete, owner management) or whatever C4 decides. Published-row protection (0.2: Store lifecycle) is not in Next Store and must be re-implemented for PATCH/DELETE.
9. Credential rule. Admin refuses any caller whose credential is not `session` (`createAdminSurface.ts:598`); Next `Caller.credential` carries the same value, so the check ports directly. Cookie-session mutations need `Sec-Fetch-Site`/`Origin` same-origin (shared kernel check in #1490/#1491).
10. MCP naming and surface (C7). `query_view_<name>` and `<schema>.publish` tools appear on staff MCP in #1491; Admin WebMCP (`routes` map: tool -> page) and the MCP App catalogue key tools by name, and `resultPath()` in the SPA still special-cases 0.1 names `request_publish`, `unpublish_entry`, `archive_entry` (`ui:admin/src/lib/admin-tools.ts:29`).
11. Statistics. Always 501; keep the capability false.
12. Site facts. `/site` mixes stored values (brand, title, description) and deployment values (origin, locales, icons, purposes). Next runs no boot-time sync (#1463), so where these live (generated constant vs table) is a design point of WP-S1.
13. Naming leaks. The SPA footer links to `npmjs.com/package/@aotter/mantle/v/{__MANTLE_VERSION__}` (`ui:admin/src/layout/authenticated-layout.tsx:188`), compatible with #1479 (package published as `@aotter/mantle`).
14. Roles. All Admin copy and gates use owner/editor/contributor (`ui:admin/src/features/system/staff-view.tsx:42-48`, `members-view.tsx:41`, nav at `authenticated-layout.tsx:165`, `:266-280`); #1492 intends one OSS role `staff` and an open-string `Caller.role`. Next `resolveCaller` still maps only the three names (`src/auth/caller.ts:43-44`).
